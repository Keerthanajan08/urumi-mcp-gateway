# Demo video and Round-2 walkthrough guide

Urumi asked for a video covering six things and said they'll ask you to walk through it end to end and defend your choices. This guide follows their six sections. Read it alongside `docs/DESIGN.md`, open each file it mentions, and run every command yourself once before recording.

## Before you record (checklist)
1. `make cluster build import` and `make install LLM_API_KEY=<groq key> STORES=1`. Wait for `make status` to show everything Ready (2–4 min).
2. `make venv`, then `make netpol-check` (after any laptop or Docker restart; if it fails, run `docker restart k3d-urumi-server-0`), then `make dod-check`. If both pass, the live demo will work.
3. Groq's free tier allows about 8,000 tokens per minute. Leave 10–20 s between chat prompts on camera, or the agent will visibly pause to wait out the limit. Try the chat prompts once with the real model: *"Create a product called Blue Mug for 12.50"*, *"What orders came in today?"*, *"Summarise today's orders and save the summary as a note"*.
4. Have Claude Code (or Cursor or Inspector) ready, plus a second browser profile or incognito window for user B.
5. Open terminal tabs: one for `kubectl -n urumi get pods -w`, one for commands.
6. Optional, for the bonus: create two stores 5 minutes before recording, so they're Ready.

Suggested length: 15–20 minutes. Show it working first, then explain. Don't read code on camera; point at the one function that matters.

## 1. System design and implementation (≈4 min)
**Components and responsibilities.** Show the README diagram and say one line each:
- **Store:** WordPress + WooCommerce + MariaDB.
- **woo-mcp:** our MCP server, 5 tools over the REST API.
- **notes / utils:** two more upstreams.
- **gateway:** an MCP client to all upstreams *and* an MCP server for users, plus users, keys, audit and chat.
- **dashboard.**
- **Postgres:** the gateway's state.
- **store-provisioner** (bonus).

**Definition of done, live, with two users.** Follow README → *Demo script* steps 1–7:
1. Storefront → add to cart → checkout with **Cash on delivery** → WP admin → WooCommerce → Orders.
2. **User A (admin),** Chat:
   - "Create a product called Blue Mug for 12.50" → refresh the storefront to show it.
   - Order it by hand.
   - "What orders came in today?" → the answer shows it.
   - Click a route chip to show arguments and result.
3. **Team → invite B.** Open the invite link in the other browser and set a password. As B: *My keys → Generate key* → copy the Claude Code command. In a terminal: `claude mcp add …` then `/mcp` in Claude Code to show all tools. Ask the orders question, then *"Summarise today's orders and save the summary as a note"* (two servers).
4. **Team → All keys → Revoke** B's key → B's next prompt fails (401).
5. **Servers → Disable "Utilities"** → in chat (A) and in Claude Code (B, `/mcp`), the `utils__` tools are gone. Re-enable.
6. `kubectl -n urumi scale deploy/notes-mcp --replicas=0` → within about 10 s, Servers shows **Unreachable – connection refused**. Ask the agent something that needs notes: a clear error, and woocommerce still works. Scale back to 1.
7. **Activity:** every call above, with the user, server, tool, time, duration and result; the chat calls are tagged "chat".

## 2. Kubernetes (≈3 min)
**What runs where:** `kubectl -n urumi get deploy,sts,svc,ingress,pvc,secret`
- Deployments: gateway, dashboard, woo-mcp, notes-mcp, utils-mcp, wordpress (with the setup sidecar), store-provisioner.
- StatefulSets: mariadb, postgres.
- PVCs: MariaDB data, WordPress files, Postgres, notes, store backups.
- Secret: one, `urumi-secrets`, generated by the chart locally (`templates/secrets.yaml`, kept stable across upgrades with `lookup`) and created by `deploy/prod/create-secrets.sh` in prod.
- Ingress: two, `store.` and `app.`.

**Requests, limits and probes:** `kubectl -n urumi get deploy gateway -o yaml | less` → resources, startupProbe, readinessProbe (`/readyz` checks the DB and that the first upstream check is done), livenessProbe (`/healthz`). The WordPress readiness probe checks a file written only when setup has finished.

**Public vs internal, and how it's enforced:**
- **Public** means it has an Ingress: only `store.` (WordPress) and `app.` (`/` dashboard, `/api`, `/mcp`, `/oauth`, `/.well-known` → gateway). `/metrics` is not routed.
- **Internal:** everything else is a ClusterIP Service, so there's no route in from outside.
- **NetworkPolicies** (`templates/networkpolicy.yaml`):
  - default-deny ingress
  - only Traefik reaches WordPress, dashboard and gateway
  - only the gateway reaches the MCP servers
  - only WordPress reaches MariaDB, and only the gateway reaches Postgres
  - plus egress rules, e.g. woo-mcp may reach only WordPress
- To prove it on camera:
  ```bash
  kubectl -n urumi exec deploy/woo-mcp -- python -c "import socket;socket.create_connection(('mariadb',3306),3)"   # refused
  kubectl -n urumi exec deploy/notes-mcp -- python -c "import socket;socket.create_connection(('woo-mcp',8000),3)" # fails (no egress at all, not even DNS)
  ```

## 3. MCP internals (≈3 min)
**How the gateway connects to upstreams** (`services/gateway/app/upstream.py`, `UpstreamManager._session`): for every operation it opens an MCP session over Streamable HTTP with an `httpx` client. That client carries **that server's** credential header (decrypted just then), has timeouts, and doesn't follow redirects. It sends `initialize`, the request, then closes. It's stateless: nothing to go stale, and any replica works.

**A tool call from client to store and back:**
1. Claude Code `POST /mcp` with `tools/call woocommerce__list_orders` and a Bearer key.
2. Traefik → gateway pod.
3. `McpAuth` (`mcp_endpoint.py`) hashes the key, looks up the user, and attaches a `Principal`.
4. MCP server handler → `toolsearch.handle_meta` (not a meta-tool) → `GatewayService.call_tool` (`service.py`):
   - rate limit (Postgres counter)
   - resolve the exposed name → server `woocommerce`, tool `list_orders`
   - policy check
   - `UpstreamManager.call`
5. → woo-mcp `POST /mcp` with **its** bearer token → `list_orders` → `WooClient` → `GET http://wordpress/wp-json/wc/v3/orders?after=<midnight in store tz>` with the REST key (Basic auth + `X-Forwarded-Proto: https`) → WooCommerce → MariaDB.
6. The result comes back the same way; the gateway writes an **audit** row (user, server, tool, ms, outcome) and updates metrics.

**Name collisions:** `<slug>__<tool>`, always prefixed (`notes__ping` vs `utils__ping`); hash-shortened above 64 characters (`exposed_name` in `service.py`).

**Timeouts:** 8 s for listing, 30 s per call (chart values). **Dead upstream:** the background loop marks it unreachable with the reason; its tools are withheld; calls get *"Upstream 'notes' is unreachable (…)"*; other servers are unaffected because each probe and call is independent and bounded.

## 4. Security posture (≈3 min)
**API keys:** `umk_` + 256 random bits, shown once, stored as SHA-256 (`security.py`). Revocation sets `revoked_at` and is checked on every request.

**Upstream credentials:** Fernet-encrypted in Postgres; the key lives in the Secret. Decrypted only into the outbound header. Never returned by the API (only `has_credential`), never sent to browsers or MCP clients, never in the chat context, and not forwarded from client to upstream (THREAT_MODEL, *Why client tokens are not passed through*).

**OAuth** (optional instead of keys): the 401 → metadata → dynamic registration → PKCE → hashed opaque tokens with rotating refresh tokens. Show it with `claude mcp add` **without** a header.

**What a member can and can't do:**
- **Can:** use permitted tools (see *Servers → Permissions*: make `create_product` admin-only and show it vanish for B), manage their own keys, see their own audit rows, create up to N stores.
- **Can't:** see credentials or URLs, manage servers or users, see others' keys or audit rows, or call restricted tools (hidden *and* rejected).

**A malicious or compromised MCP server:**
- **SSRF guard:** try adding `http://169.254.169.254/` or `http://postgres.urumi.svc.cluster.local:5432` in *Add server* and show the error.
- **NetworkPolicies:** an independent second layer.
- **Its content is untrusted:** hidden characters are stripped, descriptions are labelled with the server and length-capped, the system prompt says tool text is data, results are capped, permissions bound the blast radius, and everything is audited.
- **What it can still do:** a hostile public server receives the credential you gave it and can try prompt injection; mitigated, not eliminated. The next step would be human approval for write tools.

## 5. Chat agent (≈2 min)
`services/gateway/app/chat_agent.py`, `run_chat`:
1. Get **this user's** visible tools from `GatewayService` (above 40 tools, the three search meta-tools instead).
2. Send messages + tools to an OpenAI-compatible endpoint.
3. For each returned `tool_call`, execute it through `GatewayService.call_tool(user, …, source="chat")`.
4. Append the result as a `tool` message and loop, up to 6 steps. The final text plus the trace go back to the UI.

It acts as the logged-in user because the API resolves the session cookie to a `Principal`, and that same `Principal` makes every call. Same permissions, rate limit and audit as their API key; show *Activity*, where the rows say `chat` and the user's email. The browser can't send system or tool messages, and the LLM key is in the Secret.

## 6. Local-to-VPS production story (≈2 min)
Show the table in README → *Production-like VPS*: domain, TLS (cert-manager + `scheme: https`, which also makes cookies Secure and OAuth metadata https), storage class, secrets created out-of-band (`secrets.create=false` + `create-secrets.sh`), registry images, and 2 gateway replicas + HPA + PDB. Same chart, same command, different `-f`.

**Upgrade and rollback:** show `helm history urumi -n urumi`. Run or explain `make rollback-demo`:
1. **A good upgrade.** The pre-upgrade DB dump appears in `./scripts/restore-store.sh`. Rolling update, no dropped requests. The store converges to the new WordPress/WooCommerce versions.
2. **A broken upgrade.** `--atomic` rolls it back while the old gateway pods keep serving (`maxUnavailable: 0`).
3. **`helm rollback <rev>`.** Config and images return, PVC data is untouched, and if WooCommerce migrated the DB you restore the dump.

## Bonus segment (≈2 min, if you did it)
1. *Stores → Create store*. While it provisions: `kubectl get ns -l urumi.io/store`, `kubectl -n store-<slug> get pods,pvc,quota,netpol,ingress`.
2. When it's **Ready**, open the storefront (`<slug>.urumi.localtest.me`) and place an order. Show its tools `<slug>__*` in *Servers*.
3. Chat: *"Compare today's orders across my stores"* → the agent calls `woocommerce__list_orders` and `<slug>__list_orders`.
4. Delete the store: its tools disappear at once; `kubectl get ns` shows the namespace terminating and then gone, with PVs deleted.
5. Explain: the gateway only writes a row; the provisioner reconciles it.
   - **Retry and restart:** server-side apply is idempotent, secrets and the deadline are persisted, and a timeout gives a failed status with a reason.
   - **Guardrails:** per-user limit, ResourceQuota and LimitRange.
   - **Least privilege:** the ClusterRole has no Secret reads, and an admission policy confines it to `store-*` namespaces.

## Questions you're likely to get (with short answers)
- **Why REST and not WP-CLI or SQL?** It's the supported API: validation, hooks, emails, stock. It works over the network with a scoped, revocable key, and the MCP pod needs no WordPress files or DB credentials.
- **Why is the MCP endpoint stateless?** So any replica can serve any request without sticky sessions or shared session storage, and a dead upstream can't leave a stuck session. The cost is a few extra in-cluster round trips.
- **How do two replicas share the rate limit?** A per-user, per-minute counter row in Postgres, incremented atomically on each call. Tested: exactly one budget across 3 replicas.
- **What if Postgres is down?** The gateway stops being Ready (`/readyz`), so traffic stops. The rate limiter alone would degrade to a local limit rather than block.
- **Why not forward the user's token upstream?** Confused deputy, token replay and incoherent revocation; see THREAT_MODEL, *Why client tokens are not passed through*.
- **What does a member's key let them do with the WooCommerce key?** Exactly what the permitted tools do, rate-limited and audited; restricted tools are hidden and rejected.
- **What happens if an upstream hangs?** That call times out (30 s) with a clear error. Listing uses cached results plus bounded concurrent probes, so other servers are unaffected.
- **How would you handle 500 tools?** Search mode is already there (the three meta-tools, automatic above 40). Next would be embeddings for ranking, and per-user tool allow-lists.
- **Why a separate provisioner?** The gateway is internet-facing; a bug there shouldn't hand out cluster-wide rights. The provisioner has no Ingress, can't read Secrets, and the admission policy confines it to `store-*`.
- **How do you roll back safely if a WooCommerce update migrated the DB?** Every upgrade and rollback first dumps the DB; `helm rollback` returns code and config, and `restore-store.sh` restores the data if needed.
- **What if the model makes a bad tool call?** Two layers. The upstream validates arguments and returns an error the model sees and can correct. Groq also validates first and rejects the call (`tool_use_failed`); the agent then asks again, naming the required arguments (up to 3 times). Rate limits are waited out. All of it is bounded by 6 steps and a per-step timeout.
- **What's not production-ready?** No migrations framework (additive `create_all`), a fixed-window rate limit, single-replica WordPress, no human approval for write tools, and no streaming chat.
- **What would you do with another week?** Alembic migrations; human-in-the-loop approval for write tools; embedding-based tool search; per-store tool visibility (only the owner sees their store's tools); a Redis token bucket; and making the store provisioner a proper CRD + operator.
